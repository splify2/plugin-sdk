# steer-abi v1: `.so` плагина в процессе `steerd`

Версия **1.0**. Тег совместимости — `compat.steer-abi`. Заголовок — [`include/steer/plugin.h`](../include/steer/plugin.h).
Адреса `файл:строка` — steer `9f0e1fd`.

`.so` — для мест, где отдельный процесс не годится: вид с правилами в горячем пути, `emit`, `health`
и `revive` без fork, устройства ядра Linux через netlink в цикле демона (как `awg` сейчас —
`steer/src/kinds/awg.c`, его зовут `apply`, супервизор и сторож). **По умолчанию вид плагина — программа
под супервизором** ([steer-api.md](steer-api.md)); `.so` берут, только когда программа не подходит.

## Что проверено сегодня (PLUGINS.md 4.1.6, стенд)

- `steerd` динамический: `libsteer.so.<версия>`, `libsteer-wolfssl.so.<версия wolfSSL>` и musl
  (сборка — `steer/build/build-libs.sh:156-169, 186-190`, `--dynamic-linker=$INTERP`).
- `dlopen` в процессе, связанном с libsteer, работает; musl **не выгружает** библиотеки (`dlclose`
  возвращает 0, а `RTLD_NOLOAD` находит её снова) — обновить `.so` можно только перезапуском `steerd`.
- Статический musl `dlopen` не умеет: клиент `steer` статический (`build-libs.sh:226`), сборки телефона и
  стендов — тоже (`steer/src/kinds/kind.c:110-114`). Там `.so`-плагинов нет.
- libsteer экспортирует 367 внутренних символов по `steer/build/libsteer.map` (порождён
  `build/libs-exports.sh`, обещаний нет) и собирается с `-Bsymbolic` (`build-libs.sh:167-169`); внешнему
  модулю коннектора — ещё 20 символов `steer/build/exports-ext.lst:8-27`. Ядро требует **точную**
  версию модулей (`steer/src/daemon/supd.c:323-340`). Обещать такой ABI сторонним нельзя.

## Устройство

### `libsteer-plugin.so.1`

Библиотека в пакете `steer-core` с SONAME по major ABI. В ней — загрузчик `.so`, таблица
`struct steer_host_v1` и журнал падений; `steerd` связан с ней, внутреннюю libsteer наружу она не
открывает. Свой файл версий: `LIBSTEER_PLUGIN_1 { global: steer_plugin_host_*; local: *; }` — только
для `steerd` и стенда SDK.

**Плагин с ней не связывается** и с `libsteer.so` тоже: всё, что ему нужно от ядра, приходит таблицей
функций в `init`. `s2p lint` отвергает `.so` с `DT_NEEDED` на `libsteer*`. Довод: имя файла ядра
(`libsteer.so.2.1.0`) меняется с каждым выпуском, а таблица — нет; плагин обновляется отдельно от
ядра (решение В10) и наоборот. Когда появится ABI 2, `steer-core` положит рядом
`libsteer-plugin.so.2` и сможет держать `.so` обоих major через переходник. Почему не прямые символы —
[open.md](open.md), О-2.

### Экспорт плагина

Ровно один символ:

```c
const struct steer_plugin_v1 *steer_plugin_v1_entry(uint16_t host_major, uint16_t host_minor);
```

Всё остальное — скрыто: `-fvisibility=hidden` и файл версий `{ global: steer_plugin_v1_entry; local: *; }`.
Иначе символы плагина (или библиотек, которые он вкомпилировал) встали бы в одном адресном пространстве
с libsteer и `libsteer-wolfssl` и перехватывали бы их вызовы; musl версий символов не различает.

### Загрузка

1. Ядро сверяет `compat.steer-abi` манифеста со своим ABI (менеджер — ещё при установке).
2. Перед `dlopen` — запись в журнал загрузок (ниже).
3. `dlopen(<plugin>/<so.path>, RTLD_NOW | RTLD_LOCAL)`; `dlsym("steer_plugin_v1_entry")`; вызов с
   `STEER_ABI_MAJOR`, `STEER_ABI_MINOR` ядра.
4. Проверки ответа: `abi_major` равен ядерному, `abi_minor` не больше ядерного, `fingerprint` равен
   `STEER_ABI_FINGERPRINT` ядра (разрядность указателя, 64-битный `time_t`, порядок байт), `id` и
   `version` совпадают с манифестом. Не так — `.so` не используется, плагин `failed`: «warpbox.so
   собран для steer-abi 2.0, у ядра 1.3».
5. `init(host, &host_v1, why, n)` на цикле демона. Не 0 — плагин `failed` с причиной `why`.
6. Виды из `kinds` — в реестр (имена обязаны совпасть с `steer.kinds[].name` манифеста).

## Структуры

Полностью — в заголовке; здесь смысл.

### `struct steer_plugin_v1` — регистрация плагина

| Поле | Что |
|---|---|
| `size`, `abi_major`, `abi_minor`, `fingerprint` | с чем собран плагин |
| `id`, `version` | как в манифесте |
| `init`, `fini` | подъём на цикле демона; `fini` — только при остановке `steerd` |
| `kinds` | виды плагина, `NULL` в конце |
| `pre_apply` | хук pre-apply ([steer-api.md](steer-api.md), 3.4) вызовом функции |
| `on_event` | события сокета строкой JSON |
| `ctl` | свои команды сокета (`commands[].ctl` с `"prog": "so"`) |

### `struct steer_kind_v1` — вид

Соответствует `struct kind_ops` ядра (`steer/src/kinds/kind.h:131-210`) без внутренних типов:

| Поле | Как в ядре |
|---|---|
| `name`, `caps` | `kind_ops.name`, `caps` (`kind.h:132-133`); биты — те же номера, что `enum kind_cap` (`kind.h:40-67`) |
| `check` | `parse` + `check` (`kind.h:162-169`): ключи уже прошли схему манифеста |
| `emit` | `emit` (`kind.h:183`): правила — через `host->nft_rule(слот, текст)` |
| `health`, `revive` | `health`, `revive` (`kind.h:188-194`); имена для `revive` — заранее `host->resolve` |
| `apply_all`, `down_all` | `awg_apply_all`, `awg_down_all` — их сейчас зовёт `apply.c` напрямую (PLUGINS.md 7.2) |
| `status` | `status` (`kind.h:203`): не фрагмент с запятой, а JSON-объект, ядро кладёт его в `outputs.<имя>.plugin` |
| `expand` | хук разворота ([steer-api.md](steer-api.md), 3.3) |

### `struct steer_host_v1` — ядро для плагина

| Группа | Функции | Зачем |
|---|---|---|
| версии | `core_version`, `api_version` | журнал, решения о поведении |
| журнал | `log`, `vlog` | строки с приставкой `steer[<id>]` |
| память | `alloc`, `free` | ответы, которые освобождает ядро |
| спека | `out_by_name`, `out_count`, `out_at`, `out_name`, `out_kind`, `out_keys_json`, `out_conf_json`, `out_device`, `out_mark`, `out_table`, `out_owner` | только чтение; указатели живут до конца вызова |
| цикл | `watch_fd`, `unwatch_fd`, `timer`, `timer_cancel` | свои дескрипторы и таймеры на цикле демона (`steer/src/daemon/loop.c` однопоточный); свои потоки плагин может держать, но в ядро из них не звать |
| сеть | `sock_mark`, `resolve`, `http` | метка сокета по выходу (`out_underlay_mark`), разрешение имён рабочим потоком ядра (`steer/src/daemon/gaiw.c`), HTTPS ядра |
| nft | `nft_rule` | правило в цепочку слота `plugin_<id>_<слот>`; только из `emit` |
| события | `emit` | событие подписчикам сокета |
| ресурсы | `resource` | выданные метки, очереди, порты, таблицы ([steer-api.md](steer-api.md), 6) |
| status | `set_status` | поля выхода в `status` |
| сторож | `wake_watch`, `member_verdict` | внеочередной проход; приговор члену (как событие `member`) |
| каталоги | `plugin_dir`, `conf_dir`, `state_dir` | |

## Сервисы протоколам: где живёт стек TLS/QUIC/TUN

Решение В3: код протоколов (TLS, REALITY, QUIC, транспорты, стек TUN) уходит из ядра в плагины сразу.
Решение владельца 2026-10-25: **общие библиотеки нескольких плагинов (wolfSSL, стек) — одна общая
зависимость-плагин, а не копия в каждом**.

### Что куда

| Код | Сейчас | После 2.1 |
|---|---|---|
| стек TUN, пул узлов, гео (`src/tunnel/*`), транспорты (`src/proto/transport/*`), разбор ссылок (`sublink.c`) | `LIBSTEER_SRC` (`steer/build/sources.mk:213-219, 315-319`) | **плагин-библиотека `net1`**, `libs2p-net.so.1` |
| TLS 1.3, проверка сертификатов, ClientHello, REALITY, HTTP/2, QUIC (+ngtcp2), слой примитивов `scrypto.c` | `LIBSTEER_SRC`, `QUIC_SRC` (`sources.mk:177, 280-281, 315-319`) | **и в `net1`** (для протоколов), **и в ядре** (для своих нужд, ниже) |
| wolfSSL | `libsteer-wolfssl.so.<версия wolfSSL>` в `steer-core` (`build-libs.sh:156-163`) | ядро — своя копия; `net1` — вкомпилирован внутрь `libs2p-net.so.1`, символы скрыты |
| виды `vless`, `hysteria2`, протоколы прокси, `xsteer` (`src/kinds/*.c`) и дайлеры (`src/proto/<протокол>/*`) | libsteer и модули `steer-<m>` (`sources.mk:300-331`) | плагины-программы `vless`, `hysteria2`, `proxy`, `xsteer`, `warpbox`, связанные с `libs2p-net.so.1` |

`net1` — официальный плагин `type: library` (ключ роли `protocols`), `libs2p-net.so.1`, экспорт только с
приставкой `s2p_` ([manifest.md](manifest.md), «libs»). Протоколы пишут `"requires": {"plugins":
{"net1": "^1.2"}}` и находят библиотеку по `DT_RUNPATH $ORIGIN/../../net1/lib`.

Как сделано (steer, раскладка 2.1, `build/sources.mk`): исходники стека не переименованы — сборка
порождает из карты `build/net1/libs2p-net.map` заголовок `#define имя s2p_имя` и подключает его к `net1` и
к плагинам на ней. На границе — структуры исходников (`struct output`, `pool_cfg`, `platform_ops`,
транспорт, QUIC), поэтому `net1` отдаёт `s2p_net_abi()` — major/minor и отпечаток раскладки этих структур;
плагин сверяет их при запуске и отказывает строкой. Смена раскладки структуры границы — major (`net2`).
Основа стека (платформа, линия событий, JSON, `err`) живёт в `net1` в одном экземпляре на процесс.

### Почему так

- **Одна копия на роутер, а не в каждом протоколе** (решение владельца). Протоколов пять, стек и
  wolfSSL — бо́льшая часть их кода (libsteer 1,1 МБ и `libsteer-wolfssl` 0,67 МБ на x86-64 против
  17–113 КБ тонких бинарников модулей, `steer/build/libs/x86_64/`). Страницы кода общей библиотеки
  разделяются между процессами помощников.
- **Ядро держит свою копию TLS/QUIC и wolfSSL.** Они нужны ядру и без протоколов: резолвер — DoH, DoH3,
  DoQ (`DNSD_SRC`, `sources.mk:120-124`), замер групп — HTTPS (`urltls.c`, `sources.mk:320`), менеджер
  плагинов — HTTPS-клиент (`wb_https`, `steer/src/proto/warp/wbhttps.h:35`, переносится в `src/lib`),
  коннектор — TLS, REALITY и HTTP/2 по `exports-ext.lst`. Брать их у `net1` ядро не может: менеджер
  должен скачать первый плагин, когда плагинов ещё нет, а обновление `net1` в фоне не должно ронять
  DNS роутера.
- **Протоколы не берут wolfSSL у ядра.** SONAME `libsteer-wolfssl.so.5.9.4` несёт версию wolfSSL
  (`build-libs.sh:156-163`): каждое обновление wolfSSL в ядре ломало бы протоколы, а они обновляются
  отдельно (В10).
- **Отдельной `libs2p-wolfssl.so` нет.** Экспорт `wolfSSL_*` из библиотеки-плагина совпал бы по именам с
  `libsteer-wolfssl` ядра, и в процессе `steerd` (`.so`-плагин, которому нужен `net1`) вызовы ушли бы не
  в ту копию: musl версий символов не различает. Поэтому wolfSSL вкомпилирован в `libs2p-net.so.1` и
  скрыт, а наружу — только API `s2p_*`.

### Что ядро даёт протоколу

Протокол — программа ([steer-api.md](steer-api.md)): ядро даёт не функции, а **данные и действия вокруг
процесса**:

| Нужно протоколу | Как даёт ядро |
|---|---|
| своя настройка и место в сети | файл `{conf}`: ключи, имя устройства, метка, таблица, IPv6, подложка (steer-api.md, 1.4) |
| сокеты к узлу не через свой же туннель | `sock_mark` и `sock_mark_required` в `{conf}`; помощник ставит `SO_MARK` сам (как `transport_set_sock_mark` сейчас) |
| TUN | помощник открывает `/dev/net/tun` сам (он root; `requires.kernel: ["/dev/net/tun"]`). На платформе без `/dev/net/tun` ядро передаёт готовый дескриптор в `STEER_TUN_FD` (зарезервировано в API 1.0; телефон — [open.md](open.md), О-13) |
| маршрут в устройство | событие `up` с `dev`: ядро привязывает маршрут выхода (`route_up`, `supd.c:244`) |
| перехват TCP | правило ядра по `tcp-redir` и порт `tcp_port` в `{conf}` |
| здоровье, перезапуск, журнал | супервизор, evline, stderr |
| TLS, QUIC, стек | `net1` |

`.so`-плагину то же самое приходит функциями `host_v1` (`sock_mark`, `resolve`, `http`, цикл событий).

## Совместимость

- **minor добавляет, major ломает.** Новое поле — только в конец структуры, с ростом `abi_minor`.
  Каждая сторона читает поле другой стороны, только если `size` его покрывает (`STEER_HAS`). Ядро ABI
  `1.y` загружает плагин `1.x` при `x ≤ y`.
- Смысл существующей функции в пределах major не меняется; функцию, которую надо изменить, заменяет
  новая в конце (`…_2`), старая остаётся.
- Удаление поля, смена типа, порядка, смысла — major: новый `STEER_ABI_MAJOR`, новый
  `libsteer-plugin.so.<major>`, новое имя точки входа `steer_plugin_v<major>_entry`.
- `steer-abi` и `steer-api` растут независимо: `.so` описывает свой манифест тем же `plugin.json` и
  подстановками. Плагин с `so` объявляет `steer-abi`; ось `steer-api` ему нужна, только если у него есть и
  программы, подкоманды, службы, хуки или файлы nft (`s2p lint` сверяет).
- Лицензия: `.so` в `steerd` — производная работа steer (GPL-3.0, `steer/LICENSE`). Закрытому плагину
  (recheck, PLUGINS.md 9.2) — только программа.

## Поведение при падении

`.so` живёт в адресном пространстве `steerd`: уронить ядро он может, и обещать обратное нельзя. Что
ядро делает, чтобы падение не повторялось и было названо:

1. **Чей вызов.** Перед каждым входом в функцию плагина ядро пишет в глобальную переменную `id`
   плагина и время входа, после выхода — стирает.
2. **Обработчик фатальных сигналов** (`SIGSEGV`, `SIGBUS`, `SIGILL`, `SIGFPE`, `SIGABRT`) пишет в заранее
   открытый файл `<state>/plugin/so.crash` строку «`<id>` `<функция>` `<сигнал>` `<время>`» (только
   `write(2)` — безопасно в обработчике), затем возвращает действие по умолчанию и поднимает сигнал
   заново: procd перезапускает `steer`.
3. **Сторожевой поток** раз в секунду смотрит время входа: вызов дольше 5 с — та же запись и `abort()`.
   Вызовы `.so` не блокируют (сеть и имена — через `host_v1`), так что 5 с — уже зависание.
4. **При старте** ядро читает `so.crash`, переносит счётчик в `state.json` плагина. **Три падения за
   10 минут** — `.so` не загружается, плагин `failed`: «steerd падал в warpbox.so (health, SIGSEGV) —
   плагин отключён». Счётчик сбрасывает обновление плагина или явное включение человеком.
5. Пока `steerd` лежит, правила nft остаются в ядре Linux (набор не снимается падением процесса) и трафик
   идёт по последним правилам; помощники гаснут по `PR_SET_PDEATHSIG` (`supd.c:648-652`) и поднимаются с
   новым демоном.
6. Если падение случилось в `init`, плагин считается виновным с первого раза: следующий старт его не
   грузит, пока счётчик меньше трёх — грузит снова (вдруг падение было не его), с третьего — `failed`.
7. Падение `.so` в ребёнке `apply-plan` (`check`, `expand`, `pre_apply`) роняет только ребёнка: `apply`
   получает отказ с именем плагина, демон живёт.

## Сборка

`s2p build` (SDK) по шагу `cc` из `s2p.json` проекта вызывает `s2p cc --kind so`, и тот собирает `.so`
zig-ом под 10 архитектур (`steer/build/arches.sh:7-18`) с
`-fPIC -fvisibility=hidden -Wl,--version-script=<экспорт> -Wl,-z,defs -Wl,-soname,<имя файла>`; файл версий
`{ global: steer_plugin_v1_entry; local: *; }` SDK пишет сам. Загрузчик из `interp_of` (`arches.sh:22-32`)
ставится у программ, а не у `.so`. Проверка готового `.so` — `s2p lint`: машина и разрядность ELF под
архитектуру архива, ровно один экспорт `steer_plugin_v1_entry`, нет `DT_NEEDED` на `libsteer*`, нет
неразрешённых символов `steer_*`.

Стенд, который загружает `.so` в маленький хост с настоящей `libsteer-plugin.so.1` и прогоняет `init`,
`check`, `emit` под qemu-user (команда `s2p test`), **ещё не написан**: `libsteer-plugin.so.1` появится в
`steer-core` 2.1. Сейчас стенд SDK (`tests/run.sh`) проверяет ELF (`file`, `readelf`), экспорт и
повторяемость сборки.
