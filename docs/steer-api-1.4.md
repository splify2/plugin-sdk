# steer-api 1.4 — что добавлено к 1.3

Ядро steer 2.1 говорит steer-api **1.4**. Это прибавка к [steer-api.md](steer-api.md) (1.0) и
[1.1](steer-api-1.1.md)–[1.3](steer-api-1.3.md): плагин, написанный по 1.0–1.3, работает без изменений. Плагину, которому
нужно новое, пишут `compat.steer-api: "^1.4"`; ядро отвечает `steer version --json` с `"api":"1.4"`. Тест
совместимости — `sh tests/compat/run.sh --steer <каталог плагина>`.

Появилось по нужде плагина `tgws` (мост Telegram): его настройки — пул доменов, пути дата-центров, туннели WARP —
читаются потоками соединений без замка, перечитать их на ходу мост не может. До 1.4 он сам раз в две секунды смотрел на
`settings.json` и, увидев новый, выходил, а ядро поднимало его через паузу перезапуска (5 с): смена настройки
оборачивалась пятью секундами без Telegram.

## Настройки плагина в подписи перезапуска: `steer.settings`

```json
"steer": {
  "settings": "restart",
  "kinds": [ … ],
  "services": [ … ]
}
```

- **Что делает ядро.** Содержимое `conf/<id>/settings.json` (каталог настроек плагина, `STEER_PLUGIN_CONF`,
  [splify2-api.md](splify2-api.md), `settings.schema`) входит в подпись перезапуска **всех** помощников выходов и всех
  служб плагина — так же, как `{conf}` выхода (steer-api.md, 1.4) и файлы ключей `x-watch`. Файла нет — у подписи свой
  знак, поэтому появление и удаление файла тоже меняют её. Сверка помощников (`steer reload`, `apply`) видит другую
  подпись и поднимает помощника заново **сразу**, без паузы перезапуска.
- **Что делает хост.** Записав настройки (метод каркаса `plugin_settings_set`, служба хоста `settings set`), хост у
  плагина с `steer.settings: "restart"` зовёт `steer reload`. Без хоста — то же руками: записать файл и
  `steer reload`.
- **Что делает плагин.** Читает `settings.json` один раз при старте и за файлом не следит. Значения — только
  `"restart"`; другое значение — отказ манифеста («steer.settings — только «restart»…»).
- Плагину, который перечитывает настройки сам (как служба `recheck`), поле не нужно: без него подпись настроек не
  касается, и запись настроек никого не перезапускает.
- **Ядро старше 1.4** поле не знает: помощник после смены настроек жил бы со старыми до своего перезапуска. Поэтому
  плагин с `steer.settings` пишет `compat.steer-api: "^1.4"` (`s2p lint` отказывает при диапазоне, в который входит
  1.3).

## Отставленные пути: `kinds[].paths`

```json
{ "name": "tgws", "health": "events", "paths": true, … }
```

Помощник, который сам отставляет пути до цели (событие `health` с `dc`, `media`, `domain`, `cool` —
[steer-api.md](steer-api.md), 2.2), объявляет это у вида. Тогда `status` выхода и ответ `steer helper <выход>` несут
`paths_down` всегда — пустым массивом, когда отставленных путей нет, — и панель отличает «путей не отставлено» от
«помощник о путях не говорит». Без `paths` поле появляется только после первого события `health`. До 1.4 ядро
узнавало мост по имени подкоманды `tgws`; теперь — только по манифесту.

## Тест совместимости

`tests/compat/steer-2.1/host.py` (API 1.4) у плагина с `steer.settings: "restart"` проверяет, что значение —
`"restart"`, что у плагина есть хоть один помощник или служба (иначе перезапускать нечего) и схема настроек
(`splify2.settings.schema`); `kinds[].paths` — логическое значение.
