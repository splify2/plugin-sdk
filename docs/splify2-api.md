# splify2-api v1: бэкенд splify2 для плагинов

Версия **1.0**. Тег совместимости — `compat.splify2-api` ([manifest.md](manifest.md)). Хост пишет свою версию API
в ответ `plugins_list` (поле `splify2_api`) и в `SPLIFY2_API` (major, число) каждой программе плагина. Правило
версий то же, что у [steer-api](steer-api.md) и [host-api](host-api.md): **minor добавляет** (новый хук, поле,
событие), **major ломает**. Плагин `^1.x` исполняется хостом с API `1.y`, если `y ≥ x`; блок `splify2` плагина с
другим major хост не применяет, а причину называет в `ext_errors` ответа `plugins_list`.

Что входит в splify2-api:

1. блок `splify2` манифеста: `priority`, `hooks`, `tasks`, `events`, `methods`, `settings` (и зарезервированные
   `luci`, `kinds`, `hide`, `deny`);
2. хуки каркаса: список, порядок, протокол, политика отказа;
3. периодические задачи вместо строк crontab в postinst;
4. события ядра: одна подписка на роутер, раздача плагинам;
5. псевдонимы и переопределения методов объекта rpcd `splify2`, таблица `methods.tsv`, `final`;
6. защита: права, безопасный режим, что бывает с упавшим хуком;
7. библиотека для shell-плагинов (`SPLIFY2_LIB`);
8. версии, [тесты совместимости](#тесты-совместимости) и что в 1.0 пока не действует.

Что здесь **не** описано: интерфейс панели ([host-api.md](host-api.md)), ядро ([steer-api.md](steer-api.md)),
методы самих плагинов (`rpc` в [manifest.md](manifest.md)).

Решения владельца, на которых стоит раздел: плагины splify2 могут **урезать, менять и переопределять логику
каркаса** (хуки, замена обработчиков, скрытие и замена экранов); SDK один на steer и splify2; у каждой версии
хоста с явными изменениями API — новая версия SDK и тесты совместимости.

## 1. Блок `splify2` манифеста

Поле верхнего уровня рядом с `steer`, `rpc`, `ui`. Нужна ось `compat.splify2-api`; плагин с блоком без неё не
применяется (`s2p lint` отказывает раньше).

```jsonc
"compat": { "splify2-api": "^1.0" },
"permissions": ["splify2.hooks", "splify2.override"],
"splify2": {
  "priority": 100,                                   // порядок хуков и обёрток: меньше — раньше
  "hooks": {
    "pre_spec_set":    { "prog": "hooks/spec",  "mode": "transform", "timeout_s": 10 },
    "pre_apply":       { "prog": "hooks/apply", "mode": "veto" },
    "post_apply":      { "prog": "hooks/apply" },
    "heal":            { "prog": "hooks/heal",  "mode": "transform" },
    "backup_sections": { "prog": "hooks/backup" },
    "support_report":  { "prog": "hooks/support" },
    "purge":           { "prog": "hooks/purge" },
    "plugin_changed":  { "prog": "hooks/changed" }
  },
  "tasks": [
    { "name": "update-subs",  "every": "10m", "prog": "bin/update-subs", "only_if": "engine-enabled" },
    { "name": "update-lists", "cron": "M 5 * * *", "jitter": "random-minute", "prog": "bin/update-lists" }
  ],
  "events": { "subscribe": ["applied", "switched", "failed"], "prog": "hooks/event" },
  "methods": {
    "alias":    { "sub_quota": "quota" },                       // splify2.sub_quota → splify2.p.<id>.quota
    "override": { "ui_get": { "prog": "rpc/ui_get", "mode": "wrap" } }
  },
  "settings": { "schema": "settings.schema.json" }
}
```

| Поле | Что |
|---|---|
| `priority` | целое, по умолчанию 100. Хуки и обёртки идут по возрастанию `priority`, при равных — по `id` плагина |
| `hooks` | хуки по именам из раздела 2; ключ с неизвестным именем — схема отвергает |
| `tasks` | периодические задачи, раздел 3 |
| `events` | подписка на события ядра, раздел 4 |
| `methods` | псевдонимы и переопределения методов, раздел 5 |
| `settings.schema` | схема настроек плагина (JSON Schema, путь внутри плагина). Одна схема — форма в каркасе LuCI и форма в Andromeda. Значения лежат в `conf/<id>/settings.json`, читают и пишут их методы каркаса `plugin_settings_get` и `plugin_settings_set` |
| `luci`, `kinds`, `hide`, `deny` | **зарезервированы** под каркас LuCI (`splify2-luci`): схема их принимает, хост 1.0 не применяет (раздел 8) |

Права (`permissions`, [manifest.md](manifest.md)): `splify2.hooks` — любой хук; `splify2.override` —
`methods.override`; `splify2.hide`, `splify2.deny` — зарезервированные поля. Карточка плагина показывает их
человеку при установке. Хук или переопределение без права в реестр не попадают.

Словари языка каркаса — отдельно: `i18n/core/<язык>.json` включённых плагинов (формат — [s2p.md](s2p.md)).

## 2. Хуки

Хост собирает **реестр** (`/var/run/splify2/ext.reg`) из манифестов включённых плагинов при любой перемене их
состава и, если файла нет или `state.json` менеджера новее, при ближайшем вызове. Хуки идут из реестра, а не
из манифестов на каждый вызов.

| Хук | Где в каркасе | Что может плагин |
|---|---|---|
| `pre_spec_set` | `spec_set`: после разбора присланной спеки во временный файл, до доскачивания списков и проверки ядром | `transform` — переписать файл (`SPLIFY2_SPEC_TMP`), результат всё равно проверит ядро; `veto` — отказать; `warn`, `observe` |
| `post_spec_set` | `spec_set`: после записи спеки | наблюдать (так плагин ставит отложенное применение) |
| `pre_apply` | `apply`: после зон фаервола и доскачивания списков, до `steer apply` | `veto` — остановить применение; `warn` — строка в ответе |
| `post_apply` | `apply` при коде ядра 0 | наблюдать |
| `post_apply_fail` | `apply` при коде ядра не 0 | наблюдать |
| `heal` | `apply` и `spec_heal`: после зашитого лечения | `transform` — поправить рабочую копию спеки; принятую ядром копию хост кладёт на место |
| `backup_sections` | архив настроек (плагин `backup`) | отдавать и принимать свои разделы архива |
| `support_report` | `support_report` | добавить раздел отчёта (без секретов) |
| `purge` | `splify2-purge` | назвать свои следы (показ) или убрать их (`--yes`) |
| `plugin_changed` | после установки, снятия, включения, выключения, обновления плагина | пересчитать своё |

### 2.1 Протокол

Программа получает на **stdin** объект `{"api": 1, "hook": "<имя>", "plugin": "<id>", "ctx": {…}}`, отвечает в
**stdout** объектом JSON с кодом 0 за срок `timeout_s` (по умолчанию 10 с). Программа запускается от root в
каталоге плагина, с окружением раздела 7 плюс `SPLIFY2_HOOK` (имя хука). Ответ:

```json
{ "ok": true, "warn": ["строка для человека"], "error": "причина отказа" }
```

`ok` — истина, если плагин не возражает. `warn` — предупреждения, хост добавляет их в ответ метода. `error` —
причина, если `ok` ложно. Остальные поля хук называет сам по таблице ниже; неизвестные хост пропускает.

| Хук | `ctx` | Дополнительно в ответе |
|---|---|---|
| `pre_spec_set` | `{"spec_tmp": "<путь>"}`; путь же в `SPLIFY2_SPEC_TMP` | — |
| `post_spec_set` | `{"rev": "<ревизия>"}` | — |
| `pre_apply` | `{"spec": "<путь JSON-вида спеки>"}` | — |
| `post_apply`, `post_apply_fail` | `{"rc": <код ядра>, "output": "<вывод>"}` | — |
| `heal` | `{"spec_tmp": "<путь рабочей копии>"}`; путь же в `SPLIFY2_SPEC_TMP` | `message` — что поправлено (в ответе `apply`) |
| `backup_sections` | `{"op": "export"}` или `{"op": "restore", "sections": {"имя": "текст"}}` | при `export`: `sections` — объект «имя → текст» |
| `support_report` | `{}` | `section: {"title": "…", "text": "…"}` |
| `purge` | `{"dry_run": true|false, "keep_config": true|false}` | `plan`: массив строк — что будет убрано (`dry_run`) или убрано |
| `plugin_changed` | `{"id": "<плагин>", "action": "install|remove|enable|disable|update"}` | — |

Имена разделов `backup_sections` — `[A-Za-z0-9_]+`, текст — обычный текст без управляющих знаков (кроме перевода
строки и табуляции). В архив раздел ложится как `[plugin <id> <имя>]`, строки текста — с отступом в один
пробел; архив с такими разделами — формат 4 (без них остаётся формат 3 и читается прежними версиями).
Плагину, которого нет на роутере, раздел не передаётся: восстановление идёт дальше, в ответе — предупреждение.

### 2.2 Режимы и исход

| Режим | Ответ `ok:false` | Ответ `warn` |
|---|---|---|
| `veto` | **отказ** операции словами `error` | предупреждение |
| `warn` | предупреждение словами `error` | предупреждение |
| `transform` | предупреждение; файл, который успел переписать плагин, остаётся | предупреждение |
| `observe` (умолчание) | только журнал | только журнал |

**Политика отказа.** Хук, который упал (код не 0), не ответил за срок или ответил не объектом JSON, **не
останавливает ничего**: строка в журнале (`logger -t splify2-ext`) и предупреждение в ответе
(«плагин X: хук Y не ответил за срок»). Плагин не должен уметь «кирпичить» применение случайно. Явное
`"critical": true` у хука меняет это: упавший, зависший или ответивший не по форме хук такого плагина
останавливает операцию; карточка плагина показывает это как право.

Хуки до операции идут под замком `state` (общий с `spec_set`, `apply`, подписками, архивом), потому что трогают
спеку; хук может вызывать методы каркаса — вложенный вызов замок уже держит родитель.

## 3. Периодические задачи

`tasks[]` заменяет строки crontab из postinst пакета. Менеджер состава плагинов (`plugin_sync`) пишет **один
размеченный блок** в `/etc/crontabs/root`:

```
# splify2-plugins begin
*/10 * * * * /usr/sbin/splify2-task <плагин> <задача>
17 5 * * * /usr/sbin/splify2-task lists-catalog update-lists
# splify2-plugins end
```

Чужие строки crontab не трогаются; плагин выключен или снят — его строк в блоке нет; последний — нет и блока.

| Поле | Что |
|---|---|
| `name` | `[a-z0-9][a-z0-9-]*`, уникально внутри плагина |
| `every` | `Nm`, `Nh`, `Nd`: `10m` → `*/10 * * * *`; `6h` → `<минута> */6 * * *`; `1d` → `<минута> 4 * * *` |
| `cron` | пять полей crontab; `M` в поле минут — минута, выбранная один раз |
| `jitter` | `random-minute` — минута выбирается случайно **один раз** и хранится в `/etc/splify2/tasks.json` (ключ `"<плагин>:<задача>"`); `none` — минута 0. Роутеры не стучатся в источник в одну секунду |
| `prog` | программа в каталоге плагина; получает окружение раздела 7, `SPLIFY2_TASK` и первым аргументом имя задачи |
| `only_if` | `engine-enabled` — автозапуск ядра включён (есть `S??steer` в `/etc/rc.d`); `spec-present` — есть спека |
| `timeout_s` | срок, по умолчанию 600 с |

Одно из `every` и `cron` обязательно. `splify2-task` берёт замок на задачу (прошлый запуск ещё идёт — второй не
стартует; брошенный замок с мёртвым процессом снимается), проверяет `only_if` и срок. В безопасном режиме
задачи не записываются и не запускаются. Постоянную службу плагин объявляет в `steer.services[]`
([manifest.md](manifest.md)), а не задачей.

## 4. События ядра

`events` подписывает плагин на события ядра ([steer-api.md](steer-api.md), «События»). Ядро держит до восьми
подписчиков, поэтому плагины не подписываются сами: хост держит **одну** службу `splify2-events`
(`steer ctl subscribe`) и раздаёт события. Служба поднимается, когда хотя бы у одного включённого плагина есть
`events`, и останавливается, когда последнего не осталось. Соединение оборвалось — подписка возобновляется
через несколько секунд; пропущенные события не повторяются.

`subscribe` — имена событий (`applied`, `switched`, `failed`, `helper-down`, …) или `*`. Программа `prog`
получает на stdin `{"api": 1, "event": {<строка события ядра как есть>}}`, ответа не требуется, код и срок
(`timeout_s`, 10 с) только в журнал. События неизвестных имён хост пропускает: список растёт в той же версии.

## 5. Методы: псевдонимы и переопределения

Все методы объекта `splify2` перечислены в **`methods.tsv`** (по строке «имя, вид[, плагин]»), и этот файл — часть
API:

| Вид | Что значит |
|---|---|
| `frame` | метод каркаса: обработчик можно обернуть или заменить (`methods.override`); имя занять нельзя |
| `final` | `plugin_*`, `plugins_*`, `repo_*`, `repos_*`, `prefs_*`: ни заменить, ни обернуть, ни взять имя |
| `fast` | быстрый путь опроса (`live`, `spec_get`, `applied_get`): диспетчер отвечает на них до чтения реестра, поэтому заменить их нельзя |
| `moved` | метод вынесен из каркаса в плагин (третья колонка): без плагина отвечает отказом `not_installed` («Нужен плагин X»), с плагином его имя берёт `methods.alias` **этого** плагина |

**Псевдонимы** (`methods.alias`: «имя на объекте `splify2` → метод `rpc.methods` плагина»):

- вынесенный из каркаса метод — только плагин, названный в `methods.tsv`, и только из официального репозитория
  (`splify2`, `splify2-core-plugins`); иначе имя занято и блок отвергается строкой в `ext_errors`;
- **новое** имя, которого у каркаса нет, — любой плагин; имя появляется в `list` объекта (после перечитки rpcd),
  а права на него (`access` метода плагина) хост записывает в ACL группы плагина `splify2-p-<id>`;
- занятое имя (каркасом, final, быстрым путём, другим плагином) — отказ с названием занявшего;
- ответ псевдонима — ответ метода плагина дословно, вход — запрос дословно (в том числе большой: через файл).

**Переопределения** (`methods.override`, право `splify2.override`; только методы вида `frame`):

| Режим | Что делает хост |
|---|---|
| `replace` | вызывает программу плагина вместо обработчика каркаса; не более одного `replace` на метод — второй отвергается с названием занявшего |
| `wrap` | вызывает обработчик каркаса и передаёт его ответ программе плагина в `SPLIFY2_NEXT` (и в файле `SPLIFY2_NEXT_FILE`); ответ программы — новый ответ. Обёрток может быть несколько: по `priority`, затем по `id` |

Программа получает метод первым аргументом, запрос — на stdin. Упавшая или ответившая не по форме замена даёт
ответ каркаса; упавшая обёртка — ответ без неё; `"critical": true` меняет первое на отказ.

## 6. Защита

- **final.** Методы `plugin_*`, `plugins_*`, `repo_*`, `repos_*`, `prefs_*` не переопределяются, не оборачиваются и
  не берутся псевдонимом: ни при каком праве. Через них человек всегда может снять плагин.
- **Права.** Хук без `splify2.hooks`, переопределение без `splify2.override` в реестр не попадают.
- **Безопасный режим** — файл `/etc/splify2/safe` или `SPLIFY2_SAFE=1` в окружении вызова. Хуки, задачи, события и
  переопределения выключены; остаются каркас, менеджер плагинов и псевдонимы вынесенных из каркаса методов
  (архив настроек и каталог списков продолжают работать). Реестр пересобирается сам при появлении и снятии файла.
- **Упавший хук** ничего не останавливает (раздел 2.2); исключение — явный `critical`.
- **Причины.** Всё, что хост не принял из блока `splify2`, записано строкой `err` реестра и приходит в
  `plugins_list.ext_errors`: нет права, версия API не та, имя занято, программы нет или она не исполняемая.

## 7. Библиотека для shell-плагинов

Хост запускает программы плагина (методы `rpc`, хуки, задачи, события, замены) с окружением:

| Переменная | Значение |
|---|---|
| `STEER_PLUGIN_ID`, `STEER_PLUGIN_DIR`, `STEER_PLUGIN_CONF` | как у методов `rpc` ([manifest.md](manifest.md)) |
| `SPLIFY2_API` | major splify2-api (`1`) |
| `SPLIFY2_LIB` | путь к `lib.sh` |
| `SPLIFY2_HOOK`, `SPLIFY2_TASK`, `SPLIFY2_EVENT` | имя хука, задачи или события |
| `SPLIFY2_SPEC_TMP` | у `pre_spec_set` и `heal`: файл спеки, который можно переписать |
| `SPLIFY2_NEXT`, `SPLIFY2_NEXT_FILE` | у `wrap`: ответ каркаса |

`. "$SPLIFY2_LIB"` даёт программе то же окружение, в котором работал код метода внутри диспетчера: швы и пути
(`SPEC`, `SUB`, `LISTS`, `STEER`, `UCI_SPLIFY2`, …), `fail`, `call_lock` (замок `state`), `need_fetch` и затем
`download` (скачивание с обходом закрытого издателя), `spec_have`, `spec_json` (JSON-вид спеки для чтения),
`spec_put` (запись спеки переводом ядра), `spec_rev`, `uci_file`, `private_file`, `sanitize_list`, jshn. Эти имена —
публичная часть splify2-api: удаление или смена смысла — major. Так вынесены из каркаса плагины `backup` и
`lists-catalog`: их программы подключают библиотеку, а код методов остался прежним.

## 8. Версии, совместимость и что в 1.0 не действует

- Ответ `plugins_list`: `host_api` (панель, [host-api.md](host-api.md)), `splify2_api` (этот раздел), `ext_errors`.
- Каждая версия splify2 с явным изменением API (строка в `methods.tsv`, поле манифеста, хук, протокол,
  переменная окружения) — новая версия splify2-api и новая версия SDK: строка в
  [`tests/compat/matrix.json`](../tests/compat/matrix.json) и каталог заглушки `tests/compat/splify2-<версия>/`.
  Старые заглушки остаются: плагин проверяется против всех версий из диапазона своего `compat`.
- **В 1.0 принимаются, но не применяются:** `splify2.luci` (виды, вкладки, замена экрана и интерфейса),
  `splify2.kinds`, `splify2.hide`, `splify2.deny`. Это точки каркаса LuCI (`splify2-luci`); их действие появится
  в 1.1 с осью `compat.splify2-luci`. Принимать их уже сейчас — чтобы плагин не менял манифест вместе с каркасом.

## Тесты совместимости

`tests/compat/splify2-<версия>/` — **заглушка хоста** заданной версии: не копия каркаса, а стенд, который
ведёт себя как он по этому разделу — таблица `methods.tsv` версии, права, разбор блока, запуск хуков по
фикстурам контекста. `sh tests/compat/run.sh <каталог плагина> [версия]` проверяет, что плагин подключится:

- блок `splify2` по схеме, ось `compat.splify2-api` включает версию, права соответствуют использованию;
- хуки: каждая программа исполняема, получает фикстуру своего контекста и обязана ответить объектом JSON с
  булевым `ok` за срок; `transform` оставляет после себя годный JSON; хук `backup_sections` на `export` отдаёт
  допустимые имена разделов; `support_report` — раздел с `text`; `purge` — `plan` массивом строк;
- методы: у каждого псевдонима и переопределения есть метод `rpc` или программа; псевдоним не занимает `final`,
  `fast`, `frame` и чужой `moved`; переопределение — только `frame`; не более одного `replace` на метод внутри плагина;
- задачи: `every` и `cron` разбираются, программа исполняема, имя уникально;
- события: `subscribe` и программа.

Хост проверяет себя в обратную сторону: CI splify2 прогоняет эти тесты на плагинах `splify2-core-plugins` против
собранной версии каркаса, и каркас не выходит, если сломал плагин из коробки.
